# DJ Screen Layout Spec (phone-landscape, Flutter)

## Adaptation verdict vs the VirtualDJ screenshots
Keep the information architecture of screenshot 2 (stacked horizontal waveforms on top, deck columns left/right, mixer center), but apply the mobile-UX cuts every shipping phone DJ app converges on:

CUT ENTIRELY: jog wheels/platters (the large circular displays in vdj-ui-1 — decorative on glass; their BPM/pitch/time readouts move into a flat deck header), VINYL/SLIP toggles, AUDIO/VIDEO/SCRATCH/MASTER tab bar, sidelist/browser strip (library stays in portrait), EDIT/TAP beatgrid buttons (deferred to the #316 correction UX), headphone-cue buttons (no split-cue routing exists in the engine — see feasibility), the second INSTRU channel-fader pair (one channel fader per deck is enough on a phone).

TRANSFORM: VDJ's rotary stem knobs (HIHAT/VOCAL/KICK/BASS) become vertical mini-sliders — VirtualDJ's own mobile manual states sliders beat dials on touch; double-tap resets to unity. Hot-cue pads and loop IN/OUT move behind a per-deck exclusive panel switcher (the djay item-18 pattern: one panel zone per deck, swapped never stacked).

KEEP: stacked beat-aligned scrolling waveforms (deck A blue top, deck B red bottom, fixed center playhead), per-deck header (BPM / pitch% / key / beat-phase counter / elapsed+remaining), thin full-track overview strip per deck (tap-to-jump), CUE + PLAY/PAUSE + SYNC per deck in the bottom corners (thumb zones), pitch fader on each outer edge with +/- nudge, crossfader bottom-center.

## Geometry budget (Pixel 10 Pro landscape = 952 x 426.67 dp)
- The device is 2856 x 1280 physical pixels at dpr 3.0, so landscape is 2856/3 = **952.0 dp** wide by 1280/3 = **426.67 dp** tall. The earlier "= 980 x 448 dp" was arithmetic error and every row/column budget derived from it was over-funded by roughly one control row. Real landscape SafeArea on this device: ~24dp top status bar, ~24dp bottom gesture bar, a ~53dp leading display cutout (159 physical px) and no trailing inset — so `DjLayout`'s `LayoutBuilder` actually receives about **899 x 378.67 dp**.
- Header metric run: the give-order as the run stops fitting is **beat phase -> key + camelot -> pitch % -> clock**, and **BPM is never dropped**. The decision is cumulative and measured (`DjDeckHeader`): the raw-width thresholds are only an outer gate, so a long key, a clock past ten minutes or an elevated `textScaler` drops a whole segment rather than ellipsising every segment together. The proportional cap is a last resort that binds only once BPM is the sole survivor.
- Row budget, derived from `constraints.maxHeight` (`client/lib/features/dj/dj_layout.dart`, `DjRowBudget`). Preferred heights are waveform stack 120dp, header + overview band 44dp, control field up to 180dp, transport 64dp. As the post-SafeArea height falls, the rows give way in this exact order: **1. control field** (the designated flexible region) 180 -> 120dp; **2. waveform stack** 120 -> 64dp; **3. header band** 44 -> 36dp, dropping the 8dp overview strip below 40dp of band height; **4. transport — never**, it is pinned at 64dp because it is the primary thumb surface. The control field is the `Column`'s only `Expanded` child, so the column cannot overflow. Below **284dp** of post-SafeArea height (64 + 36 + 120 + 64) the deck is not serviceable and paints the keyed too-small state instead.
- Column budget: every row below the waveform stack is laid out on one shared grid — `Expanded(deck A) | 12dp gutter | centre column | 12dp gutter | Expanded(deck B)` — where `centerWidth = clamp(width * 0.19, 120, 180)`. The centre column carries the mixer in the control row and the crossfader in the transport row, so the fixed centre playhead runs down the middle of that column instead of down the deck A/B divider gap. The playhead itself is a 2dp `waveformPlayhead` bar inside a 4dp box, i.e. with a 1dp `colorScheme.surface` hairline on each side: the pixels it crosses are waveform peaks in the deck lane colour, and the dark playhead token is one hue step from deck B (1.12:1), so the hairline rather than the bar is what carries the contrast against the lane. Each deck column is a 48dp pitch-fader column + 4dp + the deck panel, and the deck panels absorb narrower devices. Minimum serviceable width is **488dp** = 2 x (48 + 4 + 120) + 2 x 12 + 120.
- **Authority.** Where this spec and the shipped implementation disagreed, the split is: the **implementation** is authority for the **48dp pitch-fader column** (Material's minimum touch target; the spec's extra 8dp goes to the deck panel, which is the constrained region), and the **spec** is authority for the **180dp centre column**, which the clamp above now reaches at wide viewports in place of the shipped 128dp mixer (behind the Pixel 10 Pro's leading cutout the reference viewport resolves to ~171dp).
- Touch targets: 48dp minimum everywhere at and above the reference viewport. The control field is a roughly 8x3 main-control grid, so the panel switcher is mandatory rather than optional. Below the reference budget two controls degrade deliberately, and nothing else may: the pitch fader's nudge zones step 48 -> 40 -> 24dp and then disappear entirely (`DjPitchFader.nudgeExtentFor`), and the panel switcher's band steps 48 -> 40dp on the same rung (`DjRowBudget.panelSwitcherHeight`, taken when the control field falls below 144dp). Both keep their full 48dp target at and above the reference viewport, where the control field is >= 144dp.
- Known degradation, not yet resolved: between the 488dp minimum serviceable width and roughly 840dp the deck panel sits on its 120dp floor and the hot-cue pads fall well below 48dp (about 26 x 19dp at 490dp of width). Raising `kDjMinDeckWidth` to the width that would keep the pads at target would blank the deck on the reference device itself, so the pad grid's `childAspectRatio` is the thing to revisit — the gate is correct as it stands.

## Entry point (portrait -> landscape)
- Add a spike-branch-only, feature-gated 'DJ mode' affordance in client/lib/features/player/player_screen.dart (icon button in the now-playing header) that parks/pauses the canonical PlaybackState/QueueTimelineController session before it pushes DjScreen. This prevents its voices from sounding through the shared audio session alongside the direct prototype voices. DjScreen locks landscape and seeds deck A with the current queue item and deck B with the next. Auto-entry on device rotation is a later option — explicit button first (rotation is ambiguous with casual device handling).
- Back/pop restores portrait and returns to the player. Production playback continues through the same canonical session clips; in the spike, exiting stops the prototype voices and leaves the parked canonical session for an explicit normal-player resume.

## Degradation ladder (per constraint set in #202/#198)
- No stems yet: stems panel hidden; panel switcher shows [CUES | LOOP]; mixer is channel faders + crossfader only. This is the v1 ship state.
- No analysis (missing/pending/failed): lane falls back to peak-only waveform, no beat ticks, SYNC disabled with tooltip, quantize off, pitch fader still live, beat counter blank. Playback is never blocked.
- Unreliable downbeats (hasReliableDownbeats false — the current common case, tempo_automation.dart:117-154): beat counter shows beat pulses without bar numbers; sync does beat-level phase only, never bar-level.

## Engine feasibility
# Engine Feasibility (Android, current stack: just_audio ^0.10.5 / ExoPlayer + audio_service ^0.18.18, audio_session ^0.1.25)

Per-item verdicts:

1. TWO SIMULTANEOUS PLAYERS — EXISTS. The engine already runs up to 4 concurrent just_audio AudioPlayers + 1 warm spare (VoicePool, client/lib/core/engine/voice_pool.dart:120-131; TimelineModel.maxConcurrentVoices=4) and production crossfades run 2 voices with independent volume/rate/pitch today (PR #296). Two decks fit inside the proven cap with headroom.

2. PER-DECK RATE (pitch fader) — NEEDS-WORK. Voice.setSpeed exists per player (clamped 0.5-2.0, voice.dart:145-161) but rate is currently owned by timeline PlaybackRateAutomation segments realized by a 100ms polling loop (voice_pool.dart:663-677), and the master clock rate is hard-coded 1.0 (timeline_clock.dart:104). Change needed: a live per-voice rate override (DeckController calling Voice.setSpeed directly in the prototype; in production a `liveRateMultiplier` input on the voice-control path that composes with automation, applied immediately on fader events rather than on the poll tick). The variable-rate position math (tempo_automation.dart:473-556) is reusable for position/beat projection under a live rate.

3. PER-DECK GAIN + CROSSFADER — NEEDS-WORK (small). Voice.setVolume exists but volume is envelope-owned on the 100ms gain timer (voice_pool.dart:148-151). Change needed: a live user-gain multiplier composed with the envelope value, updated on every fader gesture event (~60Hz input) with a short slew (10-20ms ramp per step) to avoid zipper noise; equal-power crossfader curve reuses gain_envelope.dart math. ExoPlayer setVolume itself applies a short internal ramp, so this is low-risk.

4. PITCH-PRESERVING STRETCH — EXISTS functionally / NEEDS-WORK for quality. pitchMode 'preserve' = setSpeed(r)+setPitch(1) via pitchFactorForRate (tempo_automation.dart:870-874) works on-device. But the Android implementation is ExoPlayer's Sonic processor, which is speech-grade (ExoPlayer issue #6575); #261 (eliminate ramp artifacts) is OPEN. Verdict: acceptable for v1 blends at small pitch offsets (+/-8%); audible degradation beyond that. Production keylock is NEEDS-NEW-DEPENDENCY: phase-2 backend swap to flutter_soloud (MIT plugin over zlib SoLoud/miniaudio, FFI) — decisive property is that all voices mix in ONE output stream with a shared sample clock; approximate keylock = setRelativePlaySpeed(r) + PitchShift filter at -12*log2(r) semitones. Phase-3 (only if soloud quality is insufficient): custom C++ engine via dart:ffi — Oboe (Apache-2.0) callback + Signalsmith Stretch (MIT, best in the 0.75x-1.5x DJ range). License traps to avoid: Rubber Band (GPL-or-paid), SoundTouch (LGPL static-link gray zone), Superpowered (no free release license).

5. SYNC STRATEGY — NEEDS-WORK (new Dart service, existing data). Data exists: BeatGridSummary.beatsMs + BPM + downbeats per track (track_analysis.dart:1215-1340), reliability gates in ClipTempoMetadata, and (post-#313) the single effectiveTiming projection with manual corrections. Strategy: Dart port of Mixxx SyncLock — each deck implements a Syncable interface; phase expressed as beat_distance in [0,1) computed from positionMs against beatsMs; SYNC first sets rate = leaderBpm/followerBpm (with octave normalization, #262 shipped), then closes phase with a capped proportional rate adjustment (cap ~ +/-1-2% extra rate), phase correction gated on quantize. Leader = the audible/playing deck; InternalClock fallback not needed for 2 decks. LATENCY HONESTY: just_audio position reporting + ExoPlayer clock granularity means achievable phase holding is roughly +/-30-80ms, not sample-accurate. That is fine for tempo-matched blends with quantized corrections; it is NOT beat-juggle/scratch grade. Sample-tight phase (<10ms) requires the shared-sample-clock soloud backend (phase 2). The existing VoicePool drift machinery (150ms nudge window) is too coarse to reuse for deck sync — DeckSync runs its own tighter loop against player positions.

6. LOW-LATENCY CUE/SEEK — NEEDS-WORK. Buffered ExoPlayer seeks (bufferForPlayback 2s, voice.dart:59-65) over the resolver ladder are 50-200ms on local files, worse on network. Mitigations for v1: decks REQUIRE a local source — resolve through PlaybackCacheManager/offline downloads and refuse (or warn) signed-URL streaming for a loaded deck; pre-seek the paused deck to its cue point so PLAY is start-from-ready rather than seek+play; hot-cue jump on a playing deck accepts the ~100ms cost with quantize masking it. True instant cues (pad drumming) need in-memory PCM = soloud phase.

7. HEADPHONE / SPLIT-CUE — DOES NOT EXIST, defer. Single shared audio session; audition_output_route_monitor.dart only classifies routes for click latency. Android split-cue (main to BT, cue to wired/USB) is a per-stream-routing problem just_audio does not expose. Cut from v1; revisit in the soloud/Oboe phase where per-device output streams are possible.

8. STEM MIXER PLAYBACK — NEEDS-NEW-DEPENDENCY (blocked on stems5 contract + backend swap). Two decks x 5 stems = 10 synchronized voices; independent ExoPlayers cannot hold intra-deck stem phase (must be sample-locked). Realistic paths: (a) soloud backend, one voice per stem, sample-locked in one mix callback; or (b) interim: server-side pre-mixed stem-bus renders (e.g. vocals/instrumental 2-bus) keeping 2 voices per deck. The stems5-v1 artifact contract from the parallel stems exploration defines the sources; the DJ screen only reserves UI space and the DjStemPanel gating.

9. LATENCY EXPECTATIONS (Pixel 10 Pro, v1 just_audio path): output latency ~40-100ms (AudioTrack); play/pause command-to-audible ~50-150ms; volume changes ~1 buffer; setSpeed changes ~100-200ms to settle. Fine for mixing two tracks with SYNC; users will feel it on pads. State this in the epic so expectations are set before dogfood.

RECOMMENDED SEAM (both phases): the Voice abstract class (client/lib/core/engine/voice.dart:28-51) is already a deck API. Phase 1 DeckController wraps JustAudioVoice; phase 2 adds a SoLoudVoice implementation behind the same interface (new dependency: flutter_soloud, latest 3.x at implementation time) — the DJ feature code does not change. Do NOT route deck control through buildPlaybackPayload (client/lib/models/playback_payload.dart:9-39) — that bridge is lossy (#290 open); production deck state rides the QueueTimelineController byQueueItemId command path (queue_timeline_controller.dart:416-538) which is complete.

# Phased Plan

## Phase 0 — TONIGHT (prototype spike branch only; never merged)
Goal: landscape screen with two real waveform lanes scrolling from real bands3-v1 data, and two independently playing decks with pitch fader + crossfader. No sync and no persisted cue/loop state; CUES and LOOP are in-memory session controls, while an unavailable stems source keeps STEMS hidden.

This direct-two-Voice mode started as exploration-only. It has since shipped: the "DJ deck's direct-voice exception" addendum in `docs/adr/0001-playback-timeline-source-of-truth.md` supersedes the never-merge rule below and defines the scope the exception is allowed to occupy (two deck-local voices, one settings-gated entry point, canonical playback parked, voices released on exit) plus the integration path that ends it. The production-integration TODO in `dj_screen.dart` remains until that path lands.

Scope (files from the layout spec):
1. dj_screen.dart + dj_layout.dart — static landscape scaffold with all zones; panel switcher exposes functional in-memory CUES/LOOP controls and hides STEMS when its source is unavailable.
2. dj_waveform_lane.dart — instantiate TimelineWaveformPainter per deck with a per-deck TimelineViewport whose offsetMs is derived from the deck position stream each frame (copy the follow-playhead loop from AnalysisCalibrationWaveform); fixed pixelsPerSecond ~90; beat/downbeat ticks come free from the painter. Data via the existing analysis hydration path (AnalysisService + richWaveformForTrack); pick the detail tier.
3. engine/deck_controller.dart — 2 x JustAudioVoice + DefaultEngineAudioSourceResolver + PlaybackCacheManager. Fabricate the resolver's required minimal MixClip with audioSourceRef, inspect the resolved source kind, and allow only local/cache-backed sources; signed-URL fallback is refused or surfaced as a warning. play/pause/seek/setSpeed(preserve pitch)/setVolume.
4. providers/dj_session_provider.dart — prototype mode: owns the two DeckControllers directly as unmerged ADR 0001 debt; seeds decks from QueueProvider current+next; publishes DjDeckState snapshots at 30Hz.
5. dj_transport.dart, dj_pitch_fader.dart, dj_deck_header.dart, dj_crossfader.dart, dj_mixer_panel.dart, dj_hot_cue_pads.dart, and dj_loop_panel.dart — wired: CUE = seek to track start (or intro-start from AnalysisRange if present), pitch fader -> setSpeed, crossfader -> equal-power dual setVolume, and beat-quantized hot-cue/loop actions use the extracted shared snap helpers.
6. Entry: temporary spike-branch feature-gated button on player_screen.dart; park/pause the canonical PlaybackState/QueueTimelineController session before starting either prototype deck.

Evidence for the spike: runs on Pixel 10 Pro over server-mac ADB (existing dogfood path), two tracks audibly playing with independent pitch and crossfade, waveforms scrolling without jank in a quick profile trace. That is demo evidence, not ship evidence.

## Risks
- Android audio latency: ExoPlayer/just_audio gives ~40-100ms output latency plus 50-200ms buffered seeks; hot-cue and pad triggers will feel soft in v1. Mitigate: local-file-only deck sources, pre-seek paused decks to their cue point, quantized triggers to mask timing, and set the expectation explicitly in the epic; true low latency arrives only with the flutter_soloud/Oboe backend (DJ-8).
- Two-player CPU/thermal: two ExoPlayers both running Sonic time-stretch at non-1.0 rate plus 60fps waveform painting is a new sustained load profile (crossfades today are transient). Risk of thermal throttling and battery drain on long sets. Mitigate: profile a 15-minute dual-deck session on the Pixel 10 Pro as part of DJ-9; drop waveform pps or lane resolution under thermal pressure.
- Waveform 60fps: playhead-follow panning is a supported TimelineWaveformPaintCache case: its marker-cache key deliberately excludes viewport origin so a pan does not rephase density. Do not add a wider-than-screen picture or canvas-translation cache. Keep a RepaintBoundary per lane and fixed one-or-two-preset zoom; use the DJ-9 profile trace to measure actual per-frame paint cost and reduce lane resolution or pixels-per-second only if that evidence calls for it.
- UI density on small screens: phone landscape leaves roughly an 8x4 grid of 48dp targets below the waveforms; showing mixer + pads + loops simultaneously is impossible and every shipping app panel-swaps. Risks: panel-state confusion (mitigate: loud selected state on DjPanelSwitcher, transport buttons never move) and fat-finger transport hits (mitigate: keep load/browse affordances top corners, far from bottom-corner transport).
- Bottom-edge gesture collisions: the bottom-center crossfader is in Android's mandatory home/nav gesture zone, which exclusion rects cannot protect. Mitigate it with the 12dp bottom inset plus deliberate drag slop before a fader claims a gesture; test gesture nav explicitly in DJ-9. The outer pitch faders, not the crossfader, are the left/right back-gesture risk. Flutter has no built-in `setSystemGestureExclusionRects` API and the client has no current usage, so a small platform channel or plugin for eligible pitch-fader exclusion rects is deferred to DJ-9; also respect the landscape display cutout on the pitch-fader column.
- Sync trust: downbeat F1 is 0.71 (#310 pilot) - bar-phase sync against a wrong downbeat sounds worse than no sync. Mitigate: SYNC does tempo-match always, phase correction only when quantize is on and only at beat level (never bar level) until #312/#316 land; SYNC disabled with explanation when hasReliableBeatGrid is false. #313 is landed; sequencing DJ-3 after #314 is the remaining hard-gate mitigation.
- Pitch-preserve audio quality: ExoPlayer Sonic is speech-grade and #261 (ramp artifacts) is open; keylock beyond ~+/-8% will sound rough in v1. Mitigate: default pitch range +/-25% but document quality expectations; offer followTempo (vinyl) mode as fallback; DJ-8 soloud A/B is the real fix.
- Architecture debt risk: the deck owns two voices directly, which conflicts with ADR 0001's Accepted ban on another playback controller. Mitigate (as shipped): the ADR 0001 addendum scopes the exception, a default-on experimental settings toggle is the only entry point, `client/test/dj_screen_voice_release_test.dart` proves the voices are returned on exit, the ADR 0001 production-integration TODO stays in `dj_screen.dart`, and DJ-1 (projection over QueueTimelineController) is the first production ticket; also never route deck state through the lossy buildPlaybackPayload bridge while #290 remains open.
- Stems dependency risk: the stem mixer column depends on the unshipped stems5-v1 contract AND realistically on the soloud backend (10 sample-locked voices); if either slips, the center mixer must look complete without stems. The layout's hidden-not-greyed degradation handles this, but validate the stems-less layout is the one polished for v1.
- Licensing trap in phase 2+: Rubber Band is GPL-or-paid, SoundTouch is LGPL with static-link ambiguity on mobile, Superpowered has no free release tier. Stick to flutter_soloud (MIT/zlib) and, if a custom engine is ever needed, Oboe (Apache-2.0) + Signalsmith Stretch (MIT).
